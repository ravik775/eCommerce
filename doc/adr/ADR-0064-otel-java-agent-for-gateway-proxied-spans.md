# ADR-0064: Adopt the OpenTelemetry Java agent for api-gateway only, to close the proxied-route span gap

**Status**: Accepted
**Date**: 2026-08-17 19:45 IST
**Deciders**: Solution/Security Architect

## Context

ADR-0055, ADR-0056, and ADR-0063 all converged on the same underlying, structural finding: this project's *library instrumentation* approach (`micrometer-tracing-bridge-otel`, manually-wired `OpenTelemetry` SDK in `common-lib`'s `TracingAutoConfiguration`, no bytecode agent) reliably works for every directly-handled request (Servlet services' HTTP requests, the gateway's own locally-handled routes like `/actuator/prometheus`), but **never** produces an exported span for a *proxied* gateway route (`POST /order` and every other business route, routed through Spring Cloud Gateway's `NettyRoutingFilter`) — confirmed live by querying every `api-gateway` span Tempo ever ingested across a multi-hour session: 100% were locally-handled routes, 0% were proxied ones. ADR-0063's `Span.current()`-reference fix was real and correct for what it addressed (the force-trace attribute now lands on the right span object when that span exists), but it could not fix this, because the underlying span for a proxied request apparently never completes/reports at all under this instrumentation approach — not a context-propagation-timing bug, a span-lifecycle-never-finishing bug.

Both ADR-0055's and ADR-0063's "Related"/"Consequences" sections already named the two structural options for closing this class of gap without further chasing it inside library instrumentation: (a) manually wrap `NettyRoutingFilter`'s proxied call in an explicitly-created and explicitly-ended span, or (b) adopt the OpenTelemetry Java agent, which bytecode-instruments reactor-netty/Spring Cloud Gateway/WebFlux internals directly at class-load time — anchored to the actual I/O call, not to the framework's own (here, buggy) self-reporting of it.

## Decision

Adopt **(b), the OpenTelemetry Java agent — for api-gateway only, not all 5 traced services.** The other 4 (order/inventory/payment/notification-service) are already confirmed working correctly under library instrumentation (live-verified this session, ADR-0062's regression run: 19 PASS / 1-2 known WARNs / 0 FAIL). The agent has real operational cost (extra artifact to version and update, small startup/runtime overhead from bytecode rewriting, less transparent failure modes than reading your own code) that isn't justified where nothing is broken — this is a targeted fix for the one service with a proven, structural gap, not a platform-wide migration.

### What changes for api-gateway specifically

1. **New module `otel-agent-extension`** (root `pom.xml`) — a standalone jar, loaded by the agent via `-Dotel.javaagent.extensions=...` into the agent's own **isolated** extension classloader. It re-implements (does not reuse/depend on) `common-lib`'s `ErrorAlwaysSampledSpanExporter` filtering policy (error spans and `force_trace`-attributed spans always exported; successful spans sampled at a configurable rate) via the OTel SDK's `AutoConfigurationCustomizerProvider` SPI (`addSpanExporterCustomizer`). Deliberately duplicated rather than shared: pulling `common-lib` (and transitively Spring, Jakarta Servlet, Spring Cloud Gateway) into the agent's isolated classloader would be unnecessary and a real classloading-conflict risk against the agent's own shaded dependencies — the whole point of an agent extension module is to depend on nothing but the SDK's own autoconfigure-SPI surface.

2. **`api-gateway/Dockerfile`**: fetches `io.opentelemetry.javaagent:opentelemetry-javaagent:2.10.0` via `mvn dependency:copy` (goes through the same Maven-repo checksum/resolution path as every other dependency this build already trusts, rather than `curl`ing a GitHub release asset) and copies it plus the built `otel-agent-extension` jar to `/otel/` in the final image (read-only, consistent with `readOnlyRootFilesystem: true`).

3. **`k8s/base/api-gateway.yaml`**: `-javaagent:/otel/opentelemetry-javaagent.jar` appended to this pod's `JAVA_TOOL_OPTIONS`; `MANAGEMENT_TRACING_ENABLED=false` overrides `common-config`'s cluster-wide `"true"` for this pod only — disables `common-lib`'s in-process OTel SDK wiring **and** Spring Boot Actuator's own tracing auto-configuration (both gated by the same real Spring Boot property), which is required: OpenTelemetry does not support two SDKs both calling `GlobalOpenTelemetry.set(...)` in the same JVM, and the agent already installs itself as the global SDK at JVM bootstrap, before the Spring context even starts. `OTEL_SERVICE_NAME`, `OTEL_EXPORTER_OTLP_ENDPOINT`/`_PROTOCOL`, `OTEL_TRACES_SAMPLER=always_on` (same `AlwaysOnSampler` reasoning as the library-instrumentation setup — the export-time filter needs every span actually recorded), `OTEL_METRICS_EXPORTER=none` / `OTEL_LOGS_EXPORTER=none` (this project uses Prometheus/Loki for those, not OTel — without this the agent would also try to OTLP-export both, redundantly), and `OTEL_JAVAAGENT_EXTENSIONS` pointing at the extension jar.

### What does NOT change

`CorrelationTraceGatewayFilter` (ADR-0055/ADR-0063's fixes) is untouched — it already uses the plain `io.opentelemetry.api` (`Span.current()`, `TraceId.isValid()`, etc.), which works identically regardless of which SDK backs `GlobalOpenTelemetry` under the hood. If anything, `Span.current()` reads should now be *more* reliable than ADR-0063's already-fixed version, since the agent's bytecode-level context propagation is exactly the mechanism that was unreliable under library instrumentation — kept the captured-`Span`-reference pattern anyway since it's still correct and there's no reason to revert a working fix.

## Regression guard

- `otel-agent-extension`'s own unit tests (`ForceTraceAndErrorSamplingExtensionTest`, mirroring `ErrorAlwaysSampledSpanExporterTest`'s cases): error spans always exported, `force_trace`-attributed spans always exported, unforced successful spans dropped at a 0% sample rate.
- `./scripts/regression-sanity.sh`'s existing `check_gateway_force_trace_span` (ADR-0063) and `check_tempo_span_attributes` (ADR-0056) checks are the actual regression guard for this ADR — both should flip from WARN to PASS once this is live-verified (see below), without any script changes needed, since they were already checking the exact right thing.
- Live verification: pending as of this entry — rebuild/redeploy api-gateway with the agent, then repeat the same 3-force-traced-order test used to catch ADR-0063's first fix attempt being incomplete, checking raw Tempo trace JSON for a genuine `api-gateway` span on a proxied route (`POST /order`), not just `/actuator/prometheus`.

### 2026-08-17 21:05 IST update — live-verified, genuinely closed (after one false result caught and fixed)

**Build hardening along the way**: the `otel-agent-extension` module's own test initially hand-implemented `AutoConfigurationCustomizer` (the OTel SDK's SPI interface) with an anonymous class. This broke Docker's fresh-cache build twice on two *different* missing-abstract-method compile errors (`addPropertiesSupplier`, then `addSamplerCustomizer`) as the resolved SDK version picked up interface methods neither the local `.m2` cache nor the extension's own logic used. Fixed properly, not patched method-by-method: `ErrorAlwaysSampledDelegatingExporter` (the actual filtering policy) was made a package-visible top-level class, and the test now constructs and exercises it directly — no SPI interface implementation involved at all, so it's no longer coupled to that interface's evolution.

**A false verification result, caught and corrected**: after the image rebuilt successfully and `kubectl rollout restart deployment/api-gateway` reported success, a 3-force-traced-order test found only 1/3 had a real `api-gateway` span — looking like an incomplete fix. Investigation (checking the actual pod's env vars, not just trusting the rollout status) found the real cause: **`kubectl rollout restart` does not pick up local YAML edits** — it restarts pods using whatever Deployment spec is already live in the cluster. The `k8s/base/api-gateway.yaml` edits from earlier in this ADR (the `-javaagent` flag, `MANAGEMENT_TRACING_ENABLED=false`, every `OTEL_*` var) had never actually been applied via `kubectl apply -f`. The pod was still running the *old* image under the *old* config — the agent was never attached at all, and the 1/3 "success" was just the old library-instrumentation path's already-known intermittent rate (matching ADR-0063's earlier 1/3 finding) coincidentally recurring, not the agent partially working.

**Corrected and re-verified**: ran `kubectl apply -f k8s/base/api-gateway.yaml`, confirmed via the pod's actual `env` list that `JAVA_TOOL_OPTIONS` now contains `-javaagent:/otel/opentelemetry-javaagent.jar` and every `OTEL_*` var is present, then repeated the exact same test: **3 of 3** force-traced `POST /order` requests had a genuine `api-gateway` span in their raw Tempo trace JSON (`rootTraceName` values like `"POST order-service"`, `"http post"` — confirmed proxied-route spans, not just `/actuator/prometheus`).

**Full regression suite** (`./scripts/regression-sanity.sh`): **19 PASS, 2 WARN, 0 FAIL**. `check_gateway_force_trace_span` (ADR-0063) — **PASS**, genuinely closed. `check_tempo_span_attributes` (ADR-0056) — still WARNed once in this run, but for a *different* reason than before: `payment-service` (pre-existing sampling variance — its Kafka-consumer span isn't itself force-traced, only the gateway's own span is, so it's still subject to the regular 10% success-sample rate; unrelated to this ADR) and `api-gateway` (a check-design mismatch, not a real gap — api-gateway deliberately never sets an `orderId` span attribute by design, per ADR-0056's own Decision text: "the gateway never learns it"). **Fixed the script**: `check_tempo_span_attributes` no longer checks `api-gateway` for `orderId` — that was never a fair test of what the gateway actually guarantees; its span *existence* is correctly and separately covered by `check_gateway_force_trace_span`. The remaining WARN (Grafana port-forward not active in this session, and payment-service's independent sampling variance) is unrelated to this ADR. Also spot-checked: `order-service`'s image still builds cleanly (`--no-cache`) after the reactor `pom.xml` change adding `otel-agent-extension` as a new module.

Both ADR-0056's and ADR-0063's remaining `api-gateway` gaps are now genuinely closed, live-verified against real Tempo data — not just theoretically fixed.

## Consequences

- Positive, once live-verified: closes both ADR-0056's and ADR-0063's remaining `api-gateway` gaps with the same fix, since they're the same root cause — attributes on a span that's now actually being created and exported for proxied routes will simply be visible, no separate attribute-path fix needed.
- Negative / accepted: api-gateway now has two structurally different tracing pipelines in this project (agent-based for the gateway, library-instrumentation-based for the other 4 services) rather than one uniform mechanism — a real maintenance-surface increase, accepted because the alternative (migrating all 5 to the agent, or accepting the gateway's gap indefinitely) is worse: the other 4 services aren't broken, and leaving the gateway broken means the one hop every request passes through has no trace visibility.
- Negative / accepted: the agent version (`2.10.0`) is pinned independently of the app's own OTel SDK version (1.49.0, via Spring Boot's BOM) — this is expected and fine (the agent embeds its own shaded SDK in an isolated classloader, deliberately decoupled from the app's classpath), but it is a second OTel-related version to track and update over time.
- Follow-up candidate, not undertaken: if this pattern proves valuable, the other 4 services could migrate to the agent too for a single uniform tracing mechanism — deliberately not done now, since it would touch 4 working services for a benefit (mechanism uniformity) weaker than the concrete gap this ADR closes.
