# ADR-0065: Fix audit-log fields invisible in Loki (transactionId, amount, etc.)

**Status**: Accepted
**Date**: 2026-08-17 21:30 IST
**Deciders**: Solution/Security Architect

## Context

Reported live: a `PAYMENT_SUCCESS` audit log line's Grafana "Fields" panel showed `app`, `auditEvent`, `container`, `detected_level`, `instance`, `job`, `namespace`, `orderId`, `pod`, `service_name` — but not `transactionId` or `amount`, even though `PaymentSagaConsumer` logs all four the same way, via the same `AuditLogger.log("PAYMENT_SUCCESS", AuditLogger.fields().with("orderId", ...).with("transactionId", ...).with("amount", ...).build())` call.

Root cause, found by reading `k8s/base/loki.yaml`'s Grafana Alloy pipeline (`loki.process "add_labels"`): it runs two `stage.regex` + `stage.labels` pairs that extract exactly five field names — `correlationId`, `traceId` (from the `[correlationId=X,traceId=Y,orderId=Z]` MDC bracket prefix every log line carries) and `auditEvent`, `orderId`, `customerId` (from a second regex matched against `AUDIT`-logger lines specifically). Every other key any `AuditLogger.Fields.with(...)` call site passes — `transactionId`, `amount`, `totalAmount`, `itemCount`, `reason`, `type`, `path`, `method`, `requiredRoles`, `authorities`, `detail`, `principal` (the full set found by grepping every `.with("...")` call across every service) — was never matched by any regex stage, so Loki never parsed it out at all. The values are genuinely present in the raw log line text (confirmed: `AuditLogger.log` writes them as plain `key=value` tokens, unredacted — `transactionId`/`amount` don't match `AuditLogger`'s own sensitive-key denylist), just never became a structured, filterable, displayed Loki field. This is not specific to payment-service or to `transactionId`/`amount` — every service's audit events beyond the three originally-promoted fields have the same gap.

## Decision

Added one new `stage.match` block to the same `loki.process "add_labels"` pipeline, scoped to lines containing `auditEvent=` (so it doesn't run against every non-audit log line for no reason):

1. **`stage.logfmt`** with an explicit `mapping` listing every additional field name found across `AuditLogger` call sites — parses them out of the line generically (the audit line's `auditEvent=X key1=val1 key2=val2 ...` portion is genuine space-separated logfmt, unlike the comma-separated `[...]` MDC bracket prefix, which is why the existing bracket-prefix extraction stays a manual regex rather than also being folded into this logfmt stage).
2. **`stage.structured_metadata`**, not `stage.labels`, for these fields. This is the deliberate, important choice: `stage.labels` promotes a value to a Loki **stream label**, which is meant for a small number of low-cardinality dimensions — the existing five (`correlationId`, `traceId`, `auditEvent`, `orderId`, `customerId`) are already a considered, bounded set. `transactionId` (effectively unique per line, a UUID) and `amount` (near-continuous) as labels would meaningfully increase Loki's series/index cardinality for no query benefit these values don't already get as searchable text. Loki's **structured metadata** (schema v13, already in use here — confirmed via `schema_config`) is the mechanism built for exactly this: per-line, searchable/filterable, and shown in Grafana's log-details Fields panel, without being part of the stream index.

Not a new field-by-field maintenance burden going forward in the same brittle way the original two-regex approach was: any *future* `AuditLogger.Fields.with(...)` key not yet in the `stage.logfmt`/`stage.structured_metadata` mapping lists will still need to be added by hand (this stage's `mapping`/`values` are explicit allowlists, not a fully generic "capture everything" pass) — a deliberate choice over auto-capturing arbitrary keys from every log line project-wide, which would risk pulling in something unexpected (e.g., a stray `=`-containing string in an unrelated log line) as a spurious field. The current list covers every field this repo's `AuditLogger` call sites actually use as of this ADR.

### 2026-08-17 22:15 IST update — two real bugs found and fixed during rollout, now live-verified

The first deployed version of this fix had two genuine bugs, both caught live rather than assumed fixed:

1. **A feedback loop.** The original `stage.match` selector, `{job="loki.source.kubernetes.pods"} |= "auditEvent="`, matched every pod's logs — including Alloy's own. Once Alloy logged a "failed to decode logfmt" error (see bug 2 below), that error message itself contained the literal text `auditEvent="..."` (quoting the line it failed to parse), which matched the same selector on the next scrape, got fed back into the same broken stage, failed again, and logged another error containing `auditEvent=` — a genuine self-sustaining loop, confirmed via a burst of repeating error lines immediately after the first rollout, and one corrupted Loki stream (`{app="loki", auditEvent="<thousands of escaped characters>"}`) left behind by it. Fixed by excluding `app="alloy"` and `app="loki"` from the selector and requiring the real `] AUDIT ` logger-name token instead of the bare, not-actually-unique substring `auditEvent=`.
2. **`stage.logfmt` doesn't tolerate non-logfmt prefixes.** Assumed (wrongly) that Go's logfmt decoder would skip over the line's leading timestamp/level/MDC-bracket text and just extract whatever valid `key=value` pairs existed later in the line. It doesn't — it hard-fails the entire decode on the first structurally-invalid token (the comma-separated `[correlationId=X,traceId=Y,orderId=Z]` bracket, or the padded logger-name field's run of spaces both broke it). Confirmed live: even after fixing bug 1's selector so only genuine AUDIT lines matched, every one of them still produced a "failed to decode logfmt" error — a hard parse failure on legitimate input, not a loop. Replaced `stage.logfmt` with the same `stage.regex` approach already proven to work for `auditEvent`/`orderId`/`customerId` — one regex, anchored on the mandatory `auditEvent=\S+` token (a regex built entirely of optional groups would trivially match an empty string at position 0 and never actually search the line — caught and fixed before this version deployed, not after), with each additional field chained as an optional trailing capture group, mirroring the existing working stage instead of introducing a new extraction mechanism.

**Also found and fixed**: the selector's very first attempt used a literal `" AUDIT :"` substring, assuming a single space of logger-name padding — the real pattern layout pads the logger name to a fixed width (`AUDIT` followed by dozens of spaces before the colon), so that literal never matched at all, silently breaking even the pre-existing `auditEvent`/`orderId`/`customerId` extraction for one rollout cycle (caught immediately by checking the stream labels on a fresh log line, not assumed fine because the config applied without error).

**Final live verification**: placed 5 fresh real orders (111–115) after the corrected rollout. Queried Loki directly: `{app="payment-service"} |= "orderId=111" | transactionId != ""` returned the line with `transactionId` and `amount` genuinely present as structured metadata (`"transactionId":"SIMULATED-CREDIT-CARD-e0c54131-...", "amount":"5.0"` in the stream's field set alongside the pre-existing `auditEvent`/`orderId` labels) — confirmed via the raw Loki API response, not just trusting that the config change "looks right." Alloy's logs settled to zero new errors (only benign, unrelated "entry too far behind" backlog-replay noise from re-scraping old pod log history on restart, present before this ADR too).

## Consequences

- Positive: every `AuditLogger` field across every service becomes genuinely searchable/visible in Grafana, not just the three that happened to be promoted when this pipeline was first written — closes a real, silent observability gap that existed since `AuditLogger` was introduced (Phase 7), not something this session's other changes newly caused.
- Positive: uses the cardinality-appropriate mechanism (structured metadata) rather than naively adding more high-cardinality Loki labels, which would have "worked" for visibility but degraded Loki's index/query performance over time as more orders/transactions accumulate.
- Negative / accepted: still an explicit allowlist, not a fully generic capture-everything stage — a genuinely new `AuditLogger` field added later needs a matching one-line addition here, same maintenance shape as before, just with a much larger already-covered set and the correct mechanism (metadata, not labels) going forward.
- Follow-up candidate, not undertaken: `stage.logfmt` could in principle be applied globally (with a small excludes-list) to auto-capture any future audit field without hand-maintaining the mapping — deliberately not done now, since the explicit-allowlist approach is more predictable and lower-risk for a config change with no automated test coverage.
